# アーキテクチャ原則

## 前提

SwiftUIは特定のMVC、MVVM、VIPER、Clean Architecture等を要求しない。そのため、このプロジェクトではパターン名から構造を決めず、SwiftUIとApple Frameworkの特性から必要な構造を導出する。

## 初期構造

```text
SwiftUI View
    │
    ├── UIローカル状態
    │
    ├── Observableなアプリ状態 / モデル（必要な場合）
    │
    ├── SwiftData
    │
    └── Application Service（複数処理の調整が必要な場合）
              │
              └── Web API Client
                     │
                     └── URLSession
```

これは固定されたレイヤー構成ではない。問題が発生していない段階で層を追加しない。

## View

Viewは表示とユーザー操作の宣言を担当する。

Viewが肥大化した場合は、責務・再利用性・状態境界を確認して分割する。

「Viewにはロジックを書いてはいけない」という機械的ルールは設けない。ただし、テストすべきビジネスルールや複雑なデータ変換をViewに閉じ込めない。

## 状態管理

状態の所有者を明確にする。

- Viewだけが必要とする短命な状態 → Viewが所有
- 複数Viewが共有する状態 → 適切な上位所有者またはObservable型
- 永続化対象 → SwiftData
- サーバーから取得した一時状態 → 要件に応じて所有者を決定

## 永続化

初期候補はSwiftDataとする。

永続化モデルがそのまま画面で利用できる場合、機械的なDTO/Domain Modelへのコピーを要求しない。

境界が必要になった時点で理由を整理する。

## Networking

標準のURLSessionを第一候補とする。

Web APIレスポンスは外部契約であるため、永続化モデルとの直接結合が変更耐性を損なう場合にはAPI DTOを設ける。

## Dependency Injection

DI Frameworkは初期導入しない。

テストや差し替えのために依存性注入が必要な箇所では、Initializer、Environment等のSwift/SwiftUI標準機構をまず検討する。

## Protocol

Protocolは「疎結合だから」という理由だけでは作らない。

次のような具体的用途がある場合に検討する。

- 複数実装が存在する
- テスト時に境界を差し替える必要がある
- 外部システムとの境界を明確化する価値がある

## 判断基準

新しい抽象化を追加するときは、次を説明できること。

1. 現在どの問題があるか。
2. その抽象化がどう解決するか。
3. 追加コストは何か。
4. より単純な方法ではなぜ不十分か。
